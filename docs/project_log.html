Project Overview

Research Objective: Develop a cooperative UAV-UGV system where an aerial vehicle provides visual guidance to a ground vehicle that lacks internal navigation sensors.

Current Implementation Status: Completed foundational click-to-move navigation with vision-based localization using ArUco fiducial markers.

System Architecture

Vision Module: Overhead camera + ArUco marker detection for UGV pose estimation

Control Module: Proportional navigation controller for autonomous waypoint following

Simulation Environment: ROS2 Humble + Gazebo Sim with TurtleBot3 platform

Development Phases

✅ Phase 0: Literature review, environment setup, control prototyping

✅ Phase 1: Odometry-based navigation (baseline)

✅ Phase 2: Vision-based localization (ArUco markers)

⏳ Phase 3: Path planning and obstacle avoidance

⏳ Phase 4: UAV integration for aerial guidance

⏳ Phase 5: Hardware deployment and field testing

Foundational Work

📚 Literature Review & Technology Selection

✓ Completed

Research Foundation

Our project is inspired by the work of Santos et al. on aerial vision-based guidance for perception-less ground vehicles. The key insight is that external visual feedback can replace expensive onboard sensors like GPS, IMU, and LIDAR.

Core Principle: A UAV equipped with a downward-facing camera tracks the UGV and computes navigation commands based on visual information alone.

Technology Stack Selection

Component Selected Technology Justification
Middleware ROS2 Humble Modern architecture, real-time capabilities, industry standard
Simulator Gazebo Sim (Ignition) Physics-accurate, sensor simulation, ROS2 integration
Vision Library OpenCV 4.x Comprehensive computer vision algorithms, ArUco support
Fiducial Markers ArUco (DICT_4X4_50) Lightweight detection, pose estimation, rotation invariance
Robot Platform TurtleBot3 Burger Differential drive, well-documented, simulation support

💡 Key Insights

  • ArUco markers provide 6-DOF pose estimation from a single camera view
  • Simulation-first approach allows rapid iteration without hardware costs
  • ROS2's DDS middleware enables distributed computing for future UAV-UGV communication

🐢 Control Algorithm Prototyping: Turtlesim

✓ Completed

Objective

Validate understanding of ROS2 pub/sub architecture and implement basic autonomous control before moving to 3D simulation.

Implementation: Safety Cage Algorithm

Developed autonomous boundary avoidance system demonstrating closed-loop feedback control.

Algorithm:

  1. Subscribe to /turtle1/pose for position feedback
  2. Compute distance to nearest boundary: d = min(x, y, 11-x, 11-y)
  3. If d < threshold: Execute emergency turn maneuver
  4. Else: Continue circular exploration pattern
def pose_callback(self, msg):
    dist_to_edge = min(msg.x, msg.y, 11-msg.x, 11-msg.y)
    
    if dist_to_edge < 0.2:
        # Emergency avoidance
        cmd = Twist()
        cmd.angular.z = 2.0
        self.vel_pub.publish(cmd)
    else:
        # Normal exploration
        cmd = Twist()
        cmd.linear.x = 1.0
        cmd.angular.z = 0.5
        self.vel_pub.publish(cmd)

⚠️ Challenge: Callback Timing & State Management

Issue: Robot exhibited "stuttering" behavior near boundaries - rapid oscillation between turning and forward motion.

Root Cause: Pose updates arriving faster than control commands could execute, causing premature state transitions.

Solution: Implemented state machine with minimum dwell time in "turning" state:

if dist_to_edge < threshold and self.state == 'normal':
    self.state = 'turning'
    self.turn_start_time = time.time()

if self.state == 'turning':
    if time.time() - self.turn_start_time > 1.0:
        self.state = 'normal'

💡 Lessons Learned

  • Asynchronous callbacks require careful state management
  • Hysteresis in control systems prevents oscillatory behavior
  • 2D prototyping validates logic before 3D complexity

📐 Camera Geometry & Visible Area Calculation

Given camera height h and FOV angle θ, the visible ground area is:

visible_width = 2 × h × tan(θ/2)
visible_width = 2 × 10 × tan(60°/2)
visible_width = 2 × 10 × tan(30°)
visible_width = 2 × 10 × 0.577
visible_width ≈ 11.55 meters

This determines the operational workspace for robot navigation.

ROS-Gazebo Bridge Configuration

Established bidirectional communication between ROS2 and Gazebo simulation:

  • /cmd_vel: ROS → Gazebo (velocity commands)
  • /overhead_camera/image: Gazebo → ROS (camera feed)
  • /odom: Gazebo → ROS (ground truth odometry)

⚠️ Challenge: Message Type Incompatibility

Symptom: Robot remained stationary despite velocity commands being published to /cmd_vel.

Debugging Process:

  1. Verified topic existence: ros2 topic list ✓
  2. Confirmed message publication: ros2 topic echo /cmd_vel ✓
  3. Checked Gazebo reception: gz topic -e /cmd_vel ✗ (No messages!)

Root Cause: Published geometry_msgs/Twist but Gazebo DiffDrive plugin expected geometry_msgs/TwistStamped with timestamp header. Plugin silently dropped unstamped messages.

Solution:

cmd = TwistStamped()
cmd.header.stamp = self.get_clock().now().to_msg()
cmd.header.frame_id = 'base_link'
cmd.twist.linear.x = velocity
cmd.twist.angular.z = angular_velocity

📐 Coordinate Transformation Mathematics

✓ Completed

📊 Image Coordinates → World Coordinates

Problem: Convert pixel coordinates (u, v) from mouse click to world coordinates (x, y) in robot frame.

Coordinate System Definitions:

  • Image Frame: Origin at top-left, u increases right, v increases down
  • World Frame: Origin at camera position, x forward (north), y left (west)

Transformation Derivation:

Step 1: Calculate scale (meters per pixel)
scale = visible_width / image_width
scale = 11.55 m / 1920 px
scale ≈ 0.00602 m/px

Step 2: Transform pixel to world coordinates
x_world = (image_height/2 - v) × scale
y_world = (image_width/2 - u) × scale

Explanation:
- (image_height/2 - v): Flip v-axis and center
- (image_width/2 - u): Flip u-axis and center
- Multiply by scale to convert pixels to meters

Example Calculation:

Click at pixel (960, 270)  [center-right of image]
x_world = (1080/2 - 270) × 0.00602 = 1.806 m  [forward]
y_world = (1920/2 - 960) × 0.00602 = 0.0 m    [centered]

Odometry-Based Pose Estimation

In Phase 1, robot pose obtained from simulation ground truth odometry:

  • Position: (x, y) from odom.pose.pose.position
  • Orientation: θ from quaternion-to-Euler conversion

Quaternion to Yaw Conversion:

def quaternion_to_yaw(q):
    siny_cosp = 2 * (q.w * q.z + q.x * q.y)
    cosy_cosp = 1 - 2 * (q.y**2 + q.z**2)
    yaw = math.atan2(siny_cosp, cosy_cosp)
    return yaw

🎮 Proportional Navigation Controller

✓ Completed

🔄 Control Law Formulation

Objective: Navigate robot from current pose (x, y, θ) to target (x_t, y_t).

Error Calculations:

Position error:
Δx = x_target - x_current
Δy = y_target - y_current
distance = √(Δx² + Δy²)

Heading error:
θ_desired = atan2(Δy, Δx)
θ_error = θ_desired - θ_current
θ_error = atan2(sin(θ_error), cos(θ_error))  # Normalize to [-π, π]

Proportional Control:

Linear velocity:
v = K_linear × distance
v = min(v, v_max)  # Saturate at maximum velocity

Angular velocity:
ω = K_angular × θ_error
ω = min(max(ω, -ω_max), ω_max)  # Saturate at ±ω_max

Tuned Parameters:

  • K_linear = 0.5 (linear gain)
  • K_angular = 1.5 (angular gain)
  • v_max = 0.5 m/s (maximum linear velocity)
  • ω_max = 1.0 rad/s (maximum angular velocity)
  • tolerance = 0.05 m (goal reached threshold)

Implementation

def control_loop(self):
    if self.target is None or self.robot_pose is None:
        return
    
    dx = self.target[0] - self.robot_pose[0]
    dy = self.target[1] - self.robot_pose[1]
    distance = math.sqrt(dx**2 + dy**2)
    
    if distance < 0.05:  # Goal reached
        self.stop_robot()
        return
    
    # Calculate desired heading
    theta_desired = math.atan2(dy, dx)
    theta_error = theta_desired - self.robot_pose[2]
    theta_error = math.atan2(math.sin(theta_error), math.cos(theta_error))
    
    # Proportional control
    cmd = TwistStamped()
    cmd.header.stamp = self.get_clock().now().to_msg()
    cmd.twist.linear.x = min(0.5 * distance, 0.5)
    cmd.twist.angular.z = max(min(1.5 * theta_error, 1.0), -1.0)
    
    self.cmd_pub.publish(cmd)

⚠️ Challenge: Gazebo Material Rendering

Problem: ArUco marker texture appeared as solid gray box in simulation despite correct file paths.

Failed Approaches:

  • Tried relative paths, absolute paths, file:// URIs - no change
  • Tested with different image formats (PNG, JPG) - still gray
  • Attempted OGRE material scripts (Classic Gazebo syntax) - incompatible
  • Checked verbose logs - no error messages (silent failure)

Root Cause: Gazebo Sim uses Ogre2 renderer which doesn't support classic OGRE material scripts. Most online tutorials target Classic Gazebo (Ogre1).

Solution: Use PBR (Physically Based Rendering) materials:

<material>
  <ambient>1 1 1 1</ambient>
  <diffuse>1 1 1 1</diffuse>
  <pbr>
    <metal>
      <albedo_map>/path/to/aruco_marker_0.png</albedo_map>
    </metal>
  </pbr>
</material>

👁️ ArUco Detection & Pose Estimation

✓ Completed

Detection Pipeline

  1. Convert camera image to grayscale
  2. Apply ArUco detection algorithm
  3. Extract marker corners (4 points)
  4. Compute marker center and orientation
def detect_aruco(self, image):
    gray = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
    
    aruco_dict = aruco.Dictionary_get(aruco.DICT_4X4_50)
    parameters = aruco.DetectorParameters_create()
    
    corners, ids, rejected = aruco.detectMarkers(
        gray, aruco_dict, parameters=parameters
    )
    
    if ids is not None and len(ids) > 0:
        return corners[0][0]  # 4 corner points
    return None

📐 Pose Calculation from Marker Corners

Given: Four corner points in image coordinates (pixels)

Calculate: Robot position (x, y) and orientation θ in world frame

Position Estimation:

Center point (pixel coordinates):
u_center = (u_tl + u_tr + u_br + u_bl) / 4
v_center = (v_tl + v_tr + v_br + v_bl) / 4

Convert to world coordinates:
x_robot = (image_height/2 - v_center) × scale
y_robot = (image_width/2 - u_center) × scale

Orientation Estimation:

Top edge vector (from top-left to top-right):
Δu = u_tr - u_tl
Δv = v_tr - v_tl

Angle in image frame:
θ_image = atan2(Δv, Δu)

Transform to world frame (accounting for 90° rotation):
θ_robot = -θ_image + π/2

⚠️ Challenge: Low Detection Rate

Initial Setup: 0.2m marker at 10m height with 640×480 camera → 60% detection rate

Analysis:

Marker size in image:
pixels = (marker_size / visible_width) × image_width
pixels = (0.2 m / 11.55 m) × 640 px
pixels ≈ 11 pixels

ArUco requirement: ~40 pixels minimum for reliable detection

Solutions Applied:

  1. Increased marker size: 0.2m → 0.5m (80% detection)
  2. Increased camera resolution: 640×480 → 1920×1080 (96% detection)

Final Configuration:

Marker size in image:
pixels = (0.5 m / 11.55 m) × 1920 px
pixels ≈ 83 pixels ✓

Detection rate: 96%

✓ Completed

System Architecture

Replaced odometry subscriber with vision-based pose estimation:

  • Input: Camera image from /overhead_camera/image
  • Processing: ArUco detection → pose calculation
  • Output: Robot pose (x, y, θ) for control loop
  • Control: Same proportional controller as Phase 1

Implementation

def image_callback(self, msg):
    # Convert ROS image to OpenCV
    image = self.bridge.imgmsg_to_cv2(msg, 'bgr8')
    
    # Detect ArUco marker
    corners = self.detect_aruco(image)
    
    if corners is not None:
        # Calculate robot pose from marker
        self.robot_pose = self.calculate_pose_from_marker(corners)
        
        # Visualize detection
        cv2.polylines(image, [corners.astype(int)], True, (0,255,0), 2)
        
        # Run control loop
        self.control_loop()
    
    # Display camera feed
    cv2.imshow('Overhead Camera', image)

🎓 Technical Contributions & Learnings

✓ Completed

💡 Key Technical Insights

  • Vision vs Odometry: Vision-based localization eliminates drift but requires line-of-sight
  • Marker Size Optimization: Trade-off between detection range and marker footprint
  • Coordinate Transformations: Careful frame management critical for spatial reasoning
  • Control Tuning: Proportional gains must balance responsiveness and stability
  • Simulation Fidelity: Gazebo Sim vs Classic Gazebo have different rendering pipelines

Challenges Overcome

  1. Message Type Compatibility: Learned importance of end-to-end verification
  2. Material Rendering: Discovered PBR materials required for Gazebo Sim
  3. Coordinate Systems: Developed systematic approach to frame transformations
  4. Detection Reliability: Optimized marker size and camera resolution
  5. State Management: Implemented hysteresis to prevent oscillations
